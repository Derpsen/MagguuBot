# AGENTS.md

Discord bot for the download side of a media homelab. Receives webhooks from **Sonarr / Radarr / Seerr / Tautulli / SABnzbd** and posts styled embeds into dedicated Discord channels. Runs as a single container on Unraid.

Scope is deliberately narrow: **downloads + Plex**. Prowlarr health belongs here because dead indexers silently break grabs. No Bazarr/Uptime/Unraid/generic — if it's not on that list, it's not in this bot.

Install on Unraid via the community-template XML (no docker-compose). Image is published to GHCR by a GitHub Action.

Human install docs live in `README.md`. This file is the agent entrypoint (stack, architecture, gotchas, channel map, slash inventory, MagguuUI FAQ, Grok Bot / Buddy, CI).

## Critical gotchas

**better-sqlite3 on Windows** — needs Python + MSVC. Locally use `npm install --ignore-scripts` to typecheck; for a runnable bot on Windows, use Docker. The Alpine Dockerfile has the build chain.

**Slash commands are per-guild** — `REST.put(Routes.applicationGuildCommands)` to `DISCORD_GUILD_ID`. Instant update, no 1h global cache. Body hash is stored in `feature_state` (`slash_commands_hash`); unchanged boots skip the PUT. Bot is single-guild by design.

**Webhook auth** — all `/webhook/*` require header `X-Magguu-Token: <WEBHOOK_SECRET>` (constant-time compared in `server/app.ts`), **except**:
- `/webhook/github` — HMAC-SHA256 via `GITHUB_WEBHOOK_SECRET` instead
- `/webhook/prowlarr` — requires `Authorization: Bearer <WEBHOOK_SECRET>` (preferred) or `?token=<WEBHOOK_SECRET>`; Prowlarr has no custom-header field so it uses the query token; keep internal/LAN-only

`/webhook/*` rate limiting is split (`src/server/webhook-guard.ts`): (1) pre-auth flood limit, 300 unauthenticated req/min per client IP, before body parsing; authenticated requests are refunded and a request with the valid shared secret passes even when its IP bucket is full, so an unauthenticated flood cannot starve real webhooks; (2) after successful auth, 600 req/min per webhook identity (route source + 12-hex SHA-256 of the credential; GitHub counts after its HMAC check via `webhookGuard.authorized`). Never log or store the raw token. Client IP = TCP socket peer (`src/server/client-ip.ts` → `src/utils/trusted-proxy.ts`, port of the Website helper). Forwarded headers (`cf-connecting-ip` → `x-forwarded-for` right-to-left, skipping trusted hops → `x-real-ip`) are used only when the socket peer is in `TRUSTED_PROXIES` (IPs/CIDRs, `private`, `none`; empty = never). `TRUST_PROXY` is legacy and ignored (startup warning). Don't downgrade the token check to plain `===`.

**Moderation authority** — `/ban`, `/kick`, `/timeout` go through `checkModerationTarget` (`src/discord/moderation-guard.ts`): no self/bot/guild-owner targets, invoker's highest role must be strictly above the target's (guild owner exempt), bot-side `bannable`/`kickable`/`moderatable`. `/announce`, `/schedule-announce`, `/purge-user`, `/purge` (View + Manage Messages + Read History) and `/slowmode` (View + Manage Channels) check the invoker's channel perms via `channel.permissionsFor(member)` (`src/discord/channel-authority.ts`); `/announce ping-role` needs a mentionable role or `MentionEveryone` in that channel. The `/warn` auto-escalation (timeout and kick) runs through the same guard (`src/discord/warn-escalation.ts`): the warning is always recorded, a denied step is skipped with a German reason in the ephemeral reply and the mod log. The central gate in `client.ts` (`default_member_permissions` vs `interaction.memberPermissions`, fail-closed on unparsable/missing values) lives in `src/discord/command-gate.ts` (`lacksCommandPermission` / `commandDenyReason`), the chat-input entry in `src/discord/command-dispatch.ts` (`dispatchChatInputCommand`, called from the exported `handleInteraction` in `client.ts`; a denial logs one `warn` with ONLY `{ command, reason }`, reason = `missing-permission` | `no-member-context` (DM) | `invalid-permission-spec`; no ids/option values; `tests/command-dispatch.test.ts` covers the wiring incl. DM fail-closed); `tests/mod-permissions.test.ts` inventories every moderation-category command (a new one without a table row fails the test) and covers missing permission, hierarchy, self/bot/owner, non-member and DM. `tests/webhook-auth.test.ts` drives the real `buildApp()` for webhook auth (token matrix, rate limit before auth, method/content-type, 1 MiB body, GitHub HMAC). New moderation commands must reuse these helpers (Discord's default-member-permissions alone is not a hierarchy check).

**Webhook retries** — failed Discord deliveries from replay-supported inbound webhooks (Sonarr, Radarr, Seerr, Tautulli, SABnzbd, GitHub, and Prowlarr) are persisted with retry metadata and replayed by the minute scheduler. Backoff is 1m, 5m, 15m, 1h, then 6h; `WEBHOOK_RETRY_MAX_ATTEMPTS` limits attempts. Replay-generated event rows reference the original event and must not recursively schedule their own retries. RSS and Blue Tracker delivery failures remain unseen and are retried on their next poll.

**Automatic backups** — the hourly scheduler creates at most one `automatic-*.db` SQLite snapshot per local day after `AUTOMATIC_BACKUP_HOUR`. Retention only prunes automatic snapshots and never deletes manual backups.

**Plex activity cards (one per Plex user)** — `plexActivity` (`🎬・plex-aktivität`) holds one bot-owned card per Plex user (since 2026-10-24; the shared single card before that is no longer edited, and before it every playback session could post its own card). Playback webhooks (`src/server/webhooks/tautulli.ts`) never post: they fold into the per-user state (`src/utils/plex-card.ts`: running sessions + last 6 finished per user, music = one `music:<user>:<player>` key, Discord-format payloads without session key = `player:<user>:<player>` via `plexPlayerCorrelationKey`; `buildPlexUserCardEmbed` renders ▶️/⏸️/💤 + name in the title, footer `PLEX_USER_CARD_FOOTER`) and `PlexCardManager` (`src/discord/plex-card-manager.ts`, wiring + SQLite store in `src/discord/plex-card.ts`, table `plex_user_card` keyed guild+channel+user_key) edits the stored message of that user only. Events without a user create no card. User resolution (`src/utils/plex-card-users.ts`): optional `PLEX_CARD_USER_ALIASES` (JSON or `name=alias,…`) and `PLEX_CARD_USER_EXCLUDE` (comma list), both matched case-insensitively and default empty; max 25 users (`PLEX_CARD_MAX_USERS`, then one throttled warn, no card for the 26th); logs carry only `plexCardTag` (8 hex of sha256), never names. A new card is posted only when a user first appears (or the message is gone: 10008/50005, or ≥5 real edit failures); posts are spaced 3 s, edits 400 ms apart (no burst at start); active users are NOT bumped to the bottom, only edited. Migration (`migrateLegacyPlexCard`, idempotent, only while the channel has no user cards): the user names of the old `plex_activity_card` state seed cards (message id null → posted one by one); the old row stays untouched. Rules per card: message id + content hash + state persist in SQLite (survives restart); trailing debounce 4 s / max wait 15 s; flush skips when the embed hash (without timestamp) is unchanged; edit is a PATCH by id (no fetch); exponential backoff per card 30 s → … max 10 min (repost cooldown 60 s after 10008, 10 min after failures); permanent Discord errors 10003/50001/50013 pause ALL cards of the channel for 30 min (one quiet `warn`, never a repost, no Discord alarm); user/player/title clipped to 40/40/150 characters and escaped when rendered; allowedMentions `{parse: []}`, `enforceEmbedTotalSize`; all Discord calls run through one promise queue; 30 s tick expires sessions without any event for 6 h and retries outstanding work; every minute the stale tick moves sessions Tautulli no longer reports (3 min grace) to "Zuletzt". Every received event still writes a `webhook_events` row (source `tautulli`). Legacy `plex_activity_messages` rows are no longer written; the old retention tick only ages them out (`PLEX_ACTIVITY_RETENTION_DAYS`). Never add a `channel.send` for playback events outside the manager.

**One-time cleanup of former Plex cards** (`src/discord/plex-card-cleanup.ts` + pure classifier `src/utils/plex-card-cleanup.ts`, state table `plex_cleanup_state`): runs from the 30 s `plex-card` tick only after all user cards are posted and in sync (≥1 posted, 0 unsynced, not paused) for a stable minute with no post in that minute, never in the creating tick. Scans the newest `PLEX_CARD_CLEANUP_SCAN_LIMIT` (default 1000) messages of the Plex channel, paginated by 100, and deletes one by one (`message.delete`, 1.2 s apart, never `bulkDelete`) only messages by the bot itself, no content, exactly one embed, not pinned, not tracked in any `*message_id` column (user cards, weekly, old single card row) and with a former Plex footer (`MagguuBot · Plex-Aktivität`, `… (eine Karte, wird aktualisiert)`, `MagguuBot · Plex activity` + author `Plex Activity …`, `MagguuBot · play|pause|resume|stop|watched|buffer|error` + author `Plex · …`). Never: user card footer, weekly, digest, `/neu`, foreign authors. 10008 = skipped, 50013 skipped (3 in a row abort), 50001 aborts at once; abort = `warn` and retry after 6 h, max 3 attempts, then `failed` (final). A run that ends with delete errors (other than 10008) is not `done`: it persists as `aborted` (or `failed` on the third attempt) and the bounded retry rescans, so only leftovers are tried again (identical classification and protection). Only a clean run persists `done` (final, survives restart). `PLEX_CARD_CLEANUP_ENABLED=false` is the emergency brake: checked in the tick and re-checked before every single delete (turning it off mid-run stops at once and persists nothing); `runPlexCardCleanupTick` takes an injectable client resolver so tests can prove a disabled cleanup never touches the client, `PLEX_CARD_CLEANUP_DRY_RUN=true` only counts (persists nothing, once per process). Log search: `Plex card cleanup: candidates found` and `Plex card cleanup finished` (field `deleted`). The per-delete `enabled` check is kept (cheap, defensive: an emergency switch flipped mid-run stops the run before the next delete) and is pinned by a wiring test that reads `deps.enabled` from the real tick, flips `PLEX_CARD_CLEANUP_ENABLED` and fails when the dep is missing or frozen at start.

**`/neu` (new on Plex)** — (failed Tautulli fetches are negative-cached for 45 s, page buttons have a 1.5 s per-user cooldown) ephemeral, paginated (8 per page, buttons `neu:<page>:<days>:<a|f|s>:<userId>`, only the invoker may flip pages) list of movies/series added to Plex in the last `tage` days (1-30, default 7, `typ` Filme/Serien/Alle). Data: Tautulli `get_recently_added` (150 entries per media type, 10 s timeout, `src/services/tautulli.ts`); Sonarr/Radarr are NOT a data source. Episodes/seasons are grouped per series (`S01 · 2 Folgen`, `Staffel 2`, `S03E04`). Pure part `src/utils/plex-new.ts` (prepare, filter, pagination, embed, customId, `safePosterUrl`), service/cache/cooldown/render `src/discord/plex-new.ts` (5 min raw cache per media type, in-flight dedupe, stale data kept when a refresh fails, 5 s per-user cooldown in memory), command `src/discord/commands/neu.ts`, buttons `src/discord/interactions/neu-buttons.ts`. Posters: never from Plex/Tautulli (thumb paths and `pms_image_proxy` need a token and are ignored); only if Radarr/Sonarr are already configured, the first item of a page gets the public `remoteUrl` poster from their library (`GET /api/v3/movie|series`, 30 min cache), and only https URLs on image.tmdb.org / artworks.thetvdb.com / assets.fanart.tv without query/credentials pass `safePosterUrl`. Errors: friendly ephemeral German text, details only in `warn` logs, never a Discord alarm. No new env, no new secret, no DB table.

**`/erinnerung` (user-defined Raid / Mythic+ / misc reminders)** — `an` (art Raid|Mythic+|Sonstiges, tag, uhrzeit `19:45`, optional text ≤100, optional `woechentlich` (default one-off), optional `kanal`), `liste`, `aus [id]` (no id = all of mine, always possible), `fortsetzen` (lifts a pause). Server-only, only on `DISCORD_GUILD_ID`, 5 s per-user creation cooldown, max 5 per user, exact duplicates refused. No Blizzard API, no assumed raid times; times are `TIME_ZONE` (default Europe/Berlin). Pure part `src/utils/raid-reminder.ts` (`zonedTimeToUtc`/`nextWeeklyOccurrence`: DST-safe via Intl — ambiguous local times fire at the first occurrence, non-existent ones shift past the gap (02:30 → 03:30) instead of being skipped; `parseReminderTime`, `sanitizeReminderText` = bidi/zero-width stripped, clipped to 100, markdown/mention-escaped; `decideDue`; embed; payload builders), manager `src/discord/raid-reminder-manager.ts` (injected store + gateway + clock: limits, tick, pause, resume, cooldown), SQLite store + Discord gateway + tick `src/discord/raid-reminders.ts`, table `raid_reminders` (`next_due_at` is the truth; created by `CREATE TABLE IF NOT EXISTS` in `src/db/client.ts`, survives restarts). Scheduler: `raid-reminders` tick every 30 s + boot tick. Delivery: DM (`allowedMentions: {parse: []}`) or the chosen channel (content `<@subscriber>`, `allowedMentions: {parse: [], users: [subscriber]}`; the user and the bot must be able to write there, `#updates` is refused; both are re-checked at SEND time: the subscriber is fetched and needs View + Send via `channel.permissionsFor(member)` (`assertSubscriberChannelAllowed`), a subscriber who lost access or left (Unknown Member 10007/10013) gets the permanent 50013 -> one pause + one warn, nothing posted, nobody pinged, no alarm; a transient member-lookup failure is retried inside the 15 min grace). Missed reminders: sent only when ≤ 15 min overdue (e.g. after a restart), older ones are skipped without a message (weekly ones are rescheduled, one-off ones dropped) — never a mass resend. After a send a weekly reminder is rescheduled from "now", a one-off one is deleted. Errors are quiet (warn logs, never an ops alarm): DM error 50007 (or 10013) pauses all of the user's DM subscriptions (`paused_reason=dm_closed`), a permanent channel error (10003/50001/50013) pauses that subscription; `/erinnerung liste` shows the pause with a friendly hint, `/erinnerung fortsetzen` re-activates from the next real date (nothing is resent). Follow-ups: `liste`/`aus` accept `nutzer` (Manage Server only, others get a refusal; moderator removals are logged); the creator gets a one-time notice (`pause_notified_at`, shown in the next `/erinnerung` reply, never a DM) when subscriptions were paused (50007 / channel problems), `fortsetzen` re-arms it; a member leaving deletes all their reminders (`guildMemberRemove`); channel delivery checks View/Send/EmbedLinks and refuses `addonUpdates` (permanent 50013 → paused once, warn log, no alarm).

## Conventions

- Embed builders return `EmbedBuilder`, never post them — posting is centralized in `server/discord-poster.ts`
- Service clients return `null` (not throw) when the service is not configured; callers decide what to do
- Activity log is append-only — no UPDATE on `webhook_events` except for retries
- Channel-ID env vars: `DISCORD_CHANNEL_*` (ALLCAPS snake_case)
- Colors live in `embeds/colors.ts` — use `Colors.sonarr/radarr/seerr/plex/sabnzbd/...` instead of hex literals
- `formatBytes` / `truncate` / `Colors` are the only embed primitives — everything else is per-domain
- **No `any`** — use `unknown` + narrow with Zod or type guards (strict mode + `noUncheckedIndexedAccess` are on)
- **No comments explaining WHAT** — only WHY, and only when non-obvious

## Healthz and Discord gateway (2026-10-26)

- `GET /healthz` (unauthenticated, no secrets) returns `{ ok, status, db, gateway }`. `gateway` = `{ ready, state (ready|starting|reconnecting), pingMs (client.ws.ping, null when unknown or down), lastReadyAt (ISO), notReadySeconds, graceSeconds, beyondGrace }`; state comes from `src/discord/gateway-health.ts` (probe `client.isReady()` plus shard events `clientReady`/`shardReady`/`shardResume` and `shardDisconnect`/`shardReconnecting`, reconciled with the live probe).
- Decision (safest variant): HTTP 200 with `status: ok` (gateway ready) or `degraded` (not ready, within the grace window; covers startup and discord.js' own reconnects). HTTP 503 `unhealthy` only when the DB check fails (as before) or the gateway has been not ready for longer than `GATEWAY_GRACE_SECONDS` (default 300, range 30-3600; never-ready is counted from process start). Reason: the Dockerfile HEALTHCHECK (30 s interval, 3 retries, `r.ok`) turns a 503 into `unhealthy` after about 90 s, so without the grace window every normal reconnect would flip it; with 300 s it only flags a real outage. Nothing in the repo restarts on unhealthy (Unraid template: `--restart=unless-stopped` ignores health; no autoheal); do NOT add an autoheal for this container: a Discord-wide outage would then restart-loop the bot and burn identify limits. `invalidated` sessions still exit by themselves.
- Tests: `tests/healthz-gateway.test.ts` (ready, startup, short outage, grace edge 300 s/301 s, recovery, missed event, DB down, no secrets/ids, exact key set).
